Setup instructions and endpoint reference for the AgriProvider Postman collection.

Version 1 · 12 November 2026 · API base URL: http://localhost:5000

Import these files

AgriProvider_API.postman_collection.json
AgriProvider_Local.postman_environment.json

The collection contains 53 requests grouped by health/authentication, provider workflows, assessor review, administrator assignments, and the learner portal. The environment has blank credential and token fields; no secrets are included.

This guide describes implemented API behavior only. It does not imply official QA, certification, eligibility, or payment functionality.

Quick setup

  1. Start the API from server/ using npm start. Confirm GET /health returns a connected database.
  2. In Postman, choose Import and import both JSON files from the repository docs/ folder.
  3. Select the AgriProvider Local environment in the top-right environment menu.
  4. Enter test values into the environment’s email, password, and, for provider registration, fullName. Do not save real secrets in a shared export.
  5. Send Health and Authentication → Login, or Register provider for a new provider account.
  6. On successful login/registration, the collection test script stores accessToken, userId, and userRole in the selected environment. Other requests use the saved bearer token.
  7. Create resources in order. Successful create requests save their IDs, such as programmeId, learnerId, enrolmentId, sessionId, and requirementId.
Requests can change data. Use an approved development database with synthetic records. Do not point mutating requests at production without explicit approval.

Authentication behavior

The collection uses bearer-token authentication for protected requests. Login and register are configured as public requests. The server issues a one-hour JWT for native/Postman usage. A successful account role is read from the database, not granted by a Postman variable.

Public registration creates provider accounts only. Learner, assessor, QA, and admin accounts must be provisioned through the approved server process. A learner login also needs an explicit or supported legacy profile link.

Web-cookie flow: browser sessions use an HttpOnly cookie, exact WEB_ORIGIN, X-Auth-Mode: cookie, and credentialed requests. Postman examples use bearer tokens; the full cookie flow is covered in the API reference PDF.

Environment variables

baseUrl defaults to http://localhost:5000. The environment also defines credentials, token, resource IDs, status filters, and request fields. Empty optional ID filters are omitted from list requests to avoid invalid UUID errors.

Common responses

400 Invalid request401 Sign-in required/rejected403 Role/origin denied404 Not found/in scope409 Conflict/state413 Too large429 Rate limited500 Internal error503 Service unavailable

  • 401 on login: check email/password and account active status. Error intentionally does not confirm whether an email exists.
  • 403: verify the signed-in role and, for assessors, active assignment.
  • 404: confirm resource IDs and that the caller owns or is assigned to the resource.
  • 409: check duplicate, workflow state, or resubmission requirements.
  • 503: check API/database connectivity and configured storage.
Not available through this API: learner uploads, announcements, QA findings/corrective actions, official certification, eligibility calculations, payment execution, and external AgriSETA/government integration.

For full field constraints, authentication cookie configuration, response details, and setup cautions, see AgriProvider_API_Documentation.pdf and server/README.md. API tests use an in-memory SQL stub; do not treat them as production database verification.
